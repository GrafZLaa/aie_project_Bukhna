# Отчёт по проекту «ПАСПОРТ.ЦИФ»

## 1. Паспорт проекта

- **Название:** ПАСПОРТ.ЦИФ — автоматизация обработки паспортов оборудования
- **Автор:** Бухна Денис
- **Контакт:** denisprotopsuper@gmail.com
- **Согласование темы:** Юрий Владимирович (одобрено в Telegram, см. переписку)
- **Краткое описание:**
  Веб-сервис, который принимает PDF/сканы паспортов оборудования и
  автономно извлекает значимые поля (наименование, код документа,
  серийные номера, даты, производитель и т.п.) для последующей загрузки
  в учётные системы (1С). Основан на связке OCR (Tesseract) +
  regex-правила + опциональная мультимодальная LLM (Ollama,
  `llama3.2-vision`).

## 2. Постановка задачи и контекст

### Предметная область

Промышленный учёт оборудования. Когда поставщик передаёт партию приборов,
вместе с ними приходит пачка PDF-паспортов — каждый со своей вёрсткой,
шрифтами, иногда отсканированный с искажениями. Оператору учётной системы
нужно вручную перепечатать ключевые поля в карточку оборудования. Это
долго, дорого, дают ошибки.

**Пользователь сервиса:** оператор склада / 1С-оператор. Сценарий:
загрузил пачку PDF → проверил извлечённые поля → нажал «Экспорт в Excel»
→ загрузил в 1С.

### Формулировка задачи в терминах ИИ

Это задача **Intelligent Document Processing / Information Extraction**:
вход — растровое/PDF-представление документа, выход — структурированный
JSON по фиксированной схеме полей. Поскольку макетов документов много и
они нестандартные, классический «обучить модель на разметке» плохо
работает (мало примеров, разная вёрстка). Поэтому подход — гибридный:

- быстрый и предсказуемый baseline на правилах;
- LLM как доскан там, где правила слабы.

### Целевые метрики

- **Field-level accuracy** на контрольной выборке (`samples/control_samples.json`).
  Для каждого документа сравниваем только поля, у которых задан непустой
  `expected`; считаем долю верно извлечённых значений. Метрика честная: она
  отражает качество там, где у нас есть истина.
- **Внутренний `quality_score`** на каждой записи: эвристическая оценка
  заполненности и согласованности полей (используется в UI как индикатор
  «нужна ли ручная проверка»).
- **Latency** прогона документа: важно для UX оператора. Цель — секунды,
  не десятки секунд (отсюда `OCR_QUALITY_SHORTCIRCUIT` и быстрый режим
  evaluation).

Почему не precision/recall в классическом смысле: «класс» здесь — это
значение поля, и оно либо совпадает с эталоном, либо нет. Это binary
match на уровне поля → accuracy и есть осмысленная агрегированная
метрика.

## 3. Данные

### Источник

Открытые PDF-паспорта реального промышленного оборудования (КЭАЗ — розетка
OptiDin, ТРЭИ — мастер-модуль М1201Е, ТеконГруп — групповой паспорт
TCC 8L), полученные как материалы хакатона. Никаких персональных данных.

### Структура

7 PDF-файлов в [`приложения/`](./приложения/):

- одиночные паспорта (с серийником и без),
- групповой паспорт,
- перечень шкафа (cabinet list),
- экранная форма исходной таблицы для заполнения,
- описание задачи.

Контрольная выборка [`samples/control_samples.json`](./samples/control_samples.json)
содержит для каждого PDF ожидаемые значения 7 ключевых полей
(`document_type`, `kod_dokumenta`, `naimenovanie`, `kod_zakaza`,
`zavodskie_nomera`, `data_vypuska`, `proizvoditel`).

### Предобработка и EDA

EDA в [`notebooks/01_eda.ipynb`](./notebooks/01_eda.ipynb). Ключевые
наблюдения:

- Корпус **маленький, разнородный** — это типичный IDP-сетап, а не задача
  «учим CNN на 10k картинок». Качество должно держаться на
  переносимости подхода, а не на запоминании.
- Часть PDF содержит embedded-текст, часть — чистые сканы. Пайплайн
  адаптивный: если embedded-текста больше `OCR_IF_EMBEDDED_CHARS=120` на
  страницу, OCR может пропускаться.
- Типы документов реально разные — под каждый в правилах
  (`_extract_structured_from_text`, `parse_cabinet_document`) прописаны
  свои эвристики (одиночный паспорт vs групповой vs шкаф).
- В контрольной выборке не каждое поле заполнено в каждом примере;
  сравниваем только непустые `expected`.

Шаги предобработки изображения (`improve_image_variants`): несколько
вариантов контрастности/бинаризации, по которым потом голосует OCR.
Это значимо повышает читаемость на бледных/перекошенных сканах.

## 4. Модели и подходы

### 4.1. Baseline: OCR + правила (без LLM)

1. PDF → изображения (PyMuPDF) и одновременно snapshot embedded-текста.
2. Каждая страница проходит multi-pass Tesseract (несколько PSM-режимов
   и вариантов предобработки), результат с лучшей эвристикой качества
   (`ocr_text_quality`) выигрывает.
3. По полному тексту работают regex/лейбловые экстракторы:
   `_pick_document_code` (TREI./БНРД./ГЖИК.… паттерны), `_extract_serials`
   (серийники с плаузибилити-скором), `_extract_dates`,
   `_extract_namenovanie`, `_extract_normative_docs`,
   `_extract_certificate_value`.
4. Финальная нормализация и санитизация (`final_cleanup`,
   `_sanitize_extracted_payload`), оценка качества записи
   (`_quality_assessment`).

Это полностью offline, CPU-only, предсказуемо, секунды на документ.

### 4.2. Improved: + локальная LLM (Ollama)

Поверх baseline:

5. Если baseline-эвристика дала низкий `quality_score` или мало полей
   (см. `_has_strong_heuristic_result`) **и** документ похож на паспорт
   (`_should_skip_llm_for_file` отсекает явно не-паспорта вроде «экранных
   форм» — экономит время), готовим страницы как base64-изображения и
   передаём в Ollama вместе с OCR-текстом.
6. Модель — `llama3.2-vision` (или альтернатива из
   `OLLAMA_MODEL_CANDIDATES` с failover). Никаких облачных API.
7. Если LLM таймаутит / Ollama недоступна — прозрачный fallback на
   baseline (`requests.RequestException → log + продолжаем`).

LLM сюда добавлена не «потому что модно», а потому что она устойчиво
выручает на двух конкретных случаях, где правила теряются: длинные
многострочные наименования с переносами и нестандартные форматы кода
заказа. На простых документах LLM не вызывается (skip-эвристики), и
сервис остаётся быстрым.

### 4.3. Что НЕ используется (и почему)

- Никаких собственных весов — корпус слишком мал, чтобы обучить что-то
  осмысленное, а готовые Tesseract + open-weight LLM покрывают задачу.
- Никаких облачных API (OpenAI/Anthropic) — требование «автономности»
  было ключевым на хакатоне и сохранено в проекте.

## 5. Экспериментальный протокол и результаты

### Протокол

- **Контроль:** 7 PDF из `приложения/`, эталоны в `samples/control_samples.json`.
- **Метрика:** field-level accuracy. Для каждого примера: число верно
  предсказанных непустых полей / общее число непустых полей в `expected`.
  Агрегируем суммой по всем примерам.
- **Компаратор:** `compare_eval_value` — нормализация регистра/пробелов,
  для списков — поэлементное сравнение нормализованных значений.
- **Прогоны:** два режима, `allow_llm=False` (baseline) и `allow_llm=True`
  (improved). Каждый прогон замеряется по времени.
- **Воспроизводимость:** [`notebooks/02_baselines.ipynb`](./notebooks/02_baselines.ipynb)
  + endpoint `/api/evaluate/default?fast=1` для быстрой self-проверки.

### Результаты

Прогоны выполнены через `GET /api/evaluate/default` (Docker, Ollama
поднята с моделью `llama3.2-vision:latest`, 6 файлов из
[`приложения/`](./приложения/), 20 непустых проверок полей):

| # | Режим           | `ENABLE_LLM` / `scan_release_date` | Поля верно / всего | Accuracy | Время  |
|---|-----------------|------------------------------------|--------------------|----------|--------|
| 1 | **Baseline**    | LLM выключена, fast-режим          | **20 / 20**        | **100 %** | 26.0 с |
| 2 | **Improved**    | LLM доступна, full-режим           | **20 / 20**        | **100 %** | 32.2 с |

Сырые JSON-замеры — [`artifacts/eval_baseline.json`](./artifacts/eval_baseline.json) и [`artifacts/eval_improved.json`](./artifacts/eval_improved.json); сводный журнал — [`artifacts/experiments_log.json`](./artifacts/experiments_log.json). Графики ниже строятся из этих же JSON скриптом [`artifacts/plot_results.py`](./artifacts/plot_results.py) и интерактивной версией в [`notebooks/02_baselines.ipynb`](./notebooks/02_baselines.ipynb).

![Время прогона контрольной выборки](./artifacts/runtime_comparison.png)

Разбивка по полям одинаковая для обоих режимов:

| Поле               | Verified | Accuracy |
|--------------------|----------|----------|
| `document_type`    | 6 / 6    | 100 %    |
| `kod_dokumenta`    | 4 / 4    | 100 %    |
| `naimenovanie`     | 4 / 4    | 100 %    |
| `proizvoditel`     | 3 / 3    | 100 %    |
| `data_vypuska`     | 1 / 1    | 100 %    |
| `kod_zakaza`       | 1 / 1    | 100 %    |
| `zavodskie_nomera` | 1 / 1    | 100 %    |

**Ключевое наблюдение по режиму Improved:** LLM **не вызвалась ни на
одном из 6 документов** — эвристика отсекала её каждый раз:

- 3 файла → `"LLM skipped: OCR+rules confidence is already high"`
  (одиночный паспорт без серийника, паспорт с серийником, групповой
  паспорт TECON TCC 8L) — baseline уже даёт высокий `quality_score`.
- 3 файла → `"LLM skipped: likely non-passport/service input"` (разбор
  паспорта, разбор паспорта из docx, экранная форма) — `_should_skip_llm_for_file`
  отсёк их по содержимому/имени, чтобы не тратить LLM на не-паспорта.

То есть на нашей контрольной выборке **LLM-этап не понадобился** —
baseline (OCR + правила) уже даёт идеальные 100 %. Разница в 6 секунд
между прогонами объясняется не LLM (она не вызывалась), а дополнительным
доскан-поиском даты выпуска по штампам (`scan_release_date=True`).

Качественные наблюдения, подтверждённые экспериментом:

- На текущем корпусе baseline (OCR + regex) полностью покрывает все 20
  полевых проверок. LLM как доскан включена и доступна, но **в этих
  условиях не активируется** — что соответствует дизайну: «LLM только
  когда правила слабы».
- Эвристики `_should_skip_llm_for_file` (по имени/содержимому) и
  `_has_strong_heuristic_result` (по `quality_score`) корректно отсекают
  LLM и экономят бюджет времени.
- Корпус небольшой (7 PDF, из них в контрольной выборке 6 с проверками),
  поэтому 100 % — оптимистичная оценка: на более широком наборе с
  плохими сканами и нестандартными вёрстками часть полей неизбежно
  потеряется, и LLM начнёт реально включаться. Расширение контрольной
  выборки — в планах развития (см. §8).

### Выбор финальной модели

В продакшн идёт **гибрид** (он и реализован в `_extract_document_payload`):

- Сначала baseline (OCR+правила) — быстро и предсказуемо.
- Если baseline даёт низкий `quality_score` или неполный набор полей,
  и документ похож на паспорт, и LLM доступна — досканиваем LLM.
- При любой проблеме с LLM — silent fallback на baseline.

Trade-off: жертвуем «потенциальной точностью на каждом документе» в
пользу средней латентности и предсказуемости (важно для оператора).

На текущей контрольной выборке гибридная схема де-факто работает как
baseline (LLM не понадобилась), и при этом сервис **по-прежнему держит
ту же 100 % accuracy быстрее на 6 секунд**. Это лучше, чем «всегда LLM»:
кладёт меньше нагрузки на инфраструктуру, держит латентность секунды, а
не десятки секунд, и не зависит от доступности Ollama в моменте.

## 6. Архитектура решения и сервис

### Пайплайн

```
PDF/изображение
   │
   ▼
[data]      рендер PDF в PNG + embedded text  (PyMuPDF)
   │
   ▼
[ocr]       multi-pass Tesseract по нескольким PSM + вариантам предобработки
   │
   ▼
[rules]     regex/лейблы → черновой dict полей + quality_score
   │
   ├──► strong heuristic? ──── да ──► финальная нормализация ──┐
   │                                                              │
   └──► слабый результат + LLM доступна ─► [llm] Ollama vision   │
                                                  │              │
                                                  ▼              │
                                         финальная нормализация ─┤
                                                                 │
                                                                 ▼
                                                    final_cleanup + score
                                                                 │
                                                                 ▼
                                         JSON (поля + _meta/_evidence/_checklist)
```

### API

См. таблицу в [`README.md`](./README.md) §4.3. Минимум по требованиям курса:

- `GET /health` — health-check.
- `POST /predict` — основной endpoint (алиас `/api/extract`), принимает
  `multipart/form-data` с полем `file`, возвращает JSON по схеме
  извлечённых полей.

### Технологии

- **Backend:** Python 3.10+, Flask 3, PyMuPDF, pytesseract, Pillow, OpenCV,
  python-barcode, openpyxl, requests, python-dotenv.
- **OCR:** Tesseract (`rus+eng`).
- **LLM:** Ollama (локально), модели семейства `llama3.2-vision` /
  `moondream`.
- **Деплой:** Docker + docker-compose (`app` + `ollama`), volumes для
  `registry_data` и `ollama_data`.

## 7. Наблюдаемость, конфигурация и безопасность

### Логи и наблюдаемость

- Стандартный `logging` (см. `log = logging.getLogger(__name__)` в `app.py`).
  Логируются ключевые события: запуск LLM, ошибки, фоллбэки, оценка качества.
- `GET /health` — простой health-check (`status`, `service`, `llm_enabled`).
- `GET /api/meta` — диагностика текущей конфигурации OCR/LLM (какие модели
  доступны в Ollama, какая активна, какие PSM в Tesseract).
- В каждом ответе extract есть `_meta` (что использовалось — OCR vs LLM,
  какие таймауты случились) и `_evidence` (откуда взялось каждое
  значение: страница + фрагмент текста).

### Конфигурация

- Все настройки вынесены в переменные окружения, шаблон —
  [`.env.example`](./.env.example).
- «Карта» значений по умолчанию для деплоя — [`configs/default.yaml`](./configs/default.yaml).
- Параметры покрывают: OCR (язык, PSM, число воркеров, таймауты, масштаб
  рендера), LLM (модели, таймауты, лимиты текста/изображений), реестр
  (пути, лимиты), Flask (host/port/debug).
- Перенастройка под другой стенд = правка одного `.env`, кода трогать не надо.

### Безопасность

- В репозитории **нет** реального `.env`, токенов, паролей — только
  `.env.example`. `.gitignore` исключает `.env`, `data/registry_state.json`,
  `data/feedback_log.jsonl`, `__pycache__`, `.venv`.
- LLM-этап работает **локально** через Ollama — нет ключей от облачных
  провайдеров, нет утечки данных паспортов наружу.
- Контролируется размер upload'ов и base64 payload'ов
  (`REGISTRY_B64_MAX`, лимиты Flask).
- Контрольный набор содержит только открытые материалы хакатона.

## 8. Ограничения и дальнейшая работа

Что осознанно осталось упрощённым:

- **Монолит** `app/app.py` частично разнесён. Чистые leaf-функции
  (нормализация серийников, парсинг дат, eval-компаратор + константы)
  физически вынесены в [`src/rules/normalize.py`](./src/rules/normalize.py),
  [`src/rules/dates.py`](./src/rules/dates.py),
  [`src/rules/_constants.py`](./src/rules/_constants.py),
  [`src/eval/compare.py`](./src/eval/compare.py) — `app.py` теперь
  импортирует их (`from src.rules.normalize import ...`). Объём `app.py`
  сократился c ~3300 до ~3060 строк, тесты остались зелёными.
  Дальнейшее разнесение (OCR-обвязка, LLM-этап, Flask-роуты) требует
  работы с глобальными конфиг-константами и Flask-объектом, поэтому
  оставлено как следующий шаг.
- **Маленький контрольный набор** (7 примеров). Цифры из
  `02_baselines.ipynb` показывают тренд, но статистически слабые.
- **MLflow / трекинг экспериментов** не подключён — фиксируем результаты
  файлами в `artifacts/`. На таком объёме это оправданно.
- **Интеграция с 1С** только в виде выгрузки JSON/Excel; реальный коннектор —
  отдельная задача.

Если бы было больше времени:

- Расширить корпус (десятки паспортов разных производителей) → честно
  замерить.
- Разнести монолит по модулям без обёрток.
- Подключить MLflow и фиксировать прогоны автоматически.
- Сравнить разные vision-LLM (`qwen2.5vl`, `moondream`, `internvl`).
- Сделать coverage-отчёт по тестам и подтянуть их до интеграционного
  e2e на реальных PDF.

## 9. Сценарий демонстрации на защите

1. `scripts/start.bat` — поднять Docker-стек.
2. Открыть UI <http://localhost:5000>, продемонстрировать загрузку
   PDF из `приложения/` (один одиночный паспорт, один групповой).
3. Показать панель полей, `quality_score`, evidence-источники.
4. Нажать «Контроль» → показать accuracy на контрольной выборке.
5. Открыть [`notebooks/02_baselines.ipynb`](./notebooks/02_baselines.ipynb)
   с таблицей baseline vs improved.
6. Показать Excel-выгрузку и 1С JSON.
7. `curl http://localhost:5000/health` — health-check.
8. `pytest tests -v` — прогон smoke-тестов.

Подробные команды — в [`README.md`](./README.md).
